# Project instructions

This is the AI Workspace repository. Start here when opening or resuming work.

1. Read [the feature map](docs/OVERVIEW.md), [shared principles](docs/PRINCIPLES.md) and [progress](docs/PROGRESS.md). Keep these compact references in context; do not load the whole specification tree or history archives. Search `docs/history/` only when past evidence or decisions are relevant, then read matching entries; expand to the full history only when requested.
2. Resume an explicitly agreed active scope from progress, checking the current files and Git state first. Use the recorded next action, relevant requirement rows, evidence and the ADRs listed for the affected features in the [ADR index](docs/architecture/decisions/README.md). If the scope is missing, contradictory or blocked by a user decision, clarify it with the user.
3. If no scope is active and the user has not selected one, start with the active [milestone](docs/MILESTONES.md) and the feature titles in the map, and discuss what to build together; prefer requirements the active milestone needs. Open only short summaries useful to that discussion. Keep selection context minimal; do not load full specs or inspect implementation code to choose a feature unless the user requests that deeper analysis. There is no preset order beyond the active milestone; explain known dependencies without inventing a delivery sequence.
4. Once the user and agent agree on a feature set and outcome, load its full specs and affected dependency/security sections, then plan, implement and verify that scope. Follow [the working agreement](docs/WORKING_AGREEMENT.md); complete authorized work without repeated approval for routine steps.
5. Before changing the app's interface, read [the UI style guide](docs/UI_STYLE.md); before creating or changing code or its documentation, read [the code documentation guide](docs/CODE_DOCS.md). When adding or changing feature definitions, read [the feature-writing guide](docs/ADDING_FEATURES.md). Specifying a feature does not authorize implementing it. If work reveals a capability that should be its own feature, suggest it to the user instead of folding it in.
6. Update current progress automatically after each completed step, agreed decision or commit; record completed work as a `docs/history/YYYY-MM-DD-NN-name/` folder with a short `SUMMARY.md` and a `DETAILS.md` for verification, update the Status line of affected feature summaries, and add or supersede ADRs in the [ADR index](docs/architecture/decisions/README.md) for decisions made. Follow [the progress/history contract](docs/WORKING_AGREEMENT.md#progress-and-history), and include affected records in the same commit. Before finishing or handing off, refresh the compact current scope, remaining work, relevant links, blockers and next concrete action plus affected traceability. Track open limits and defects as GitHub issues labelled `known-limit` (`gh issue list --label known-limit`), not as lists in docs. Keep agreed work separate from suggestions; never claim implementation or tests without evidence.

This repository is public. Never commit private data: local absolute paths, usernames, emails, credentials, tokens or machine-specific output. Use placeholders such as `<project-path>` in docs, and check the staged diff for such data before every commit.

Before every push, run `npm run typecheck` and `npm test` in `app/` and the private-data scan from `.github/workflows/ci.yml`; push only when they pass. Group a change into logical commits and push it once it is complete and verified, not as intermediate fix-ups. Keep pull requests as drafts while working and mark them ready when done: that starts the full Windows/macOS/Ubuntu checks ([CI](docs/WORKING_AGREEMENT.md#ci)).

Preserve user changes and shared security boundaries. Requirements belong in their owning specs; summaries and this file should link to details rather than duplicate them.
