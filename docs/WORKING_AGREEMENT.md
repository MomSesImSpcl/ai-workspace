# Implementation working agreement

Maintain progress, requirement traceability and ADRs whenever implementation or significant decisions change. Start each session by checking current progress, relevant requirement rows and decisions using the selective reading process below.

## Documentation ownership

- The overview is a map; summaries help select features. Neither replaces a full spec for implementation.
- Each feature folder has exactly `SUMMARY.md` and `SPEC.md`. Keep summaries short; store authoritative behavior once and link shared contracts.
- Follow [the feature-writing guide](ADDING_FEATURES.md) when defining or revising a capability; documentation changes do not authorize implementation.
- Preserve original numbered section references (for example, `4.3`); cite a numbered item or distinctive bullet when tracking individual requirements. Add stable IDs for new requirements.
- Change requirements in their owning spec, then update affected summaries, links and traceability. Resolve conflicts explicitly; do not let summaries silently override required behavior.

The implementing AI coding agent **MUST** follow this process for each agreed feature scope:

1. **Choose with minimal context** as in [AGENTS.md](../AGENTS.md) steps 1–3. Explain known dependencies, value and trade-offs; do not independently select the next feature or impose a fixed order.
2. **Load detail for agreed work:** First list open issues (`gh issue list --state open`) and name those that block or affect the agreed scope, so they are fixed first or accepted with the user. after the user and agent choose a feature set and intended outcome, read its full specs, affected dependency/security contracts, relevant traceability rows and ADRs. Inspect actual architecture, source and tests; do not assume the project is greenfield. Refine included requirements and acceptance checks together when detail raises a material choice. Write a concise plan covering affected modules, risks, migrations/security and tests; complete authorized work without repeated approval for routine steps.
3. **Prefer vertical slices.** Deliver one demonstrable user workflow end-to-end before expanding scaffolding to many theoretical modules. **Keep increments small to keep token use low.** Split each feature scope into the smallest increments that can each be built, run and checked within one session; never attempt a whole feature in one large pass. Verify each increment before starting the next, stop at the first failed check, and confirm direction with the user before costly or hard-to-reverse work. Why (agreed with the user): a large one-shot attempt can consume a big share of the daily token budget before anyone learns it failed or needs changes; small increments fail cheaply and early, which keeps total cost as low as possible. Token use is not a hard limit, but every scope should be as small as the need allows.
4. **Document decisions** in ADRs under the [decision record rules](#architecture-decision-records), separating required behavior from chosen technology. Resolve architecture, repository layout, CI/test/lint/format conventions, secrets policy and developer setup as the selected work needs them. Record unknowns and assumptions; do not invent vendor policies, licenses or capabilities. [Technology candidates](TECHNOLOGY_CANDIDATES.md) are nonbinding. Keep setup and documentation proportional to real work. Record every dependency that work adds, drops or re-tests (runtime prerequisite, npm package, agent CLI, OS piece, dev tool) in the [dependency inventory](DEPENDENCIES.md) in the same commit, with the version tested. The same applies to every setup step a user must perform once (install, login, config file, OS setting): record it in that dependency's row and, if a normal installation needs it, in the inventory's setup order.
5. **Implement behind contracts/interfaces** for models, providers, tools, runners, storage and domain integrations. Avoid speculative abstraction that has no test or actual second implementation when it can wait.
6. **Write and run tests**; report the commands, outputs and limitations. Never claim a build or visual validation passed without running it.
7. **Review security**: cross-repo ACL, untrusted data, tool permission, secrets and external data routing for any affected changes.
8. **Update docs and traceability**: re-check each open issue the work touched: close resolved ones with the fixing commit and evidence, comment on partly resolved ones with what remains; status `not-started / in-progress / validated / deferred`, actual evidence links/commits, known defects (file each open limit or defect as a GitHub issue labelled `known-limit` and `feature:<name>`, link it from the ADR/traceability row instead of restating it, and close it with the fixing commit), migration steps and any agreed follow-up. Update the **Status** line of each affected feature `SUMMARY.md` and its marker in [the overview](OVERVIEW.md). Add or supersede ADRs and update [the ADR index](architecture/decisions/README.md) for decisions made. Keep current state in progress; add a history folder for each completed step under the contract below.
9. **Review the completed scope**: show the real input-to-result workflow, reviewable artifacts, actual tests, risks, compatibility and quality limits. Discuss the next feature set with the user; do not autonomously start unrelated features or invent a future delivery sequence.
10. **Never destroy existing user work** to satisfy the task. Use branches/checkpoints/reversible migrations. Require approval before publishing, deploying, installing risky tools, changing production secrets or merging work that can overwrite another user.
11. **One branch per feature scope.** Implement each agreed feature set or slice on its own branch (`feature/<short-name>`) created from `main`; record the branch in progress. Merge into `main` only after the scope is verified and the user approves; then delete the merged branch locally and on the remote, and remove any worktree that held it once its session is done (its commits stay in `main`; record the merge commit in history). Check a worktree for uncommitted work before removing it. Small documentation or rule changes outside a feature scope may go directly to `main`. Commit and push without asking when the user's intent is clear and no questions are open; otherwise ask first.

## Progress and history

[PROGRESS.md](PROGRESS.md) is the current handoff, not a cumulative log. Aim for 300–500 words: active agreed scope/requirement links, current outcome, remaining work, blockers/open decisions, branch/commit when known, latest evidence link and next concrete action. Retain unresolved work when shortening it. Keep agreed direction separate from proposals; link owning specs, decisions and traceability instead of duplicating requirements or full plans.

Record each completed step or decision as a new folder `history/YYYY-MM-DD-NN-short-name/` (work date; `NN` orders items within a day) with two files. `SUMMARY.md`: title, 1–3 sentences of scope, outcome and status, and a link to the details. `DETAILS.md`: the dated descriptive heading, scope/requirement references, outcome and remaining issues, affected file/evidence links, actual checks/results/limitations, and branch/commit when known (otherwise explicitly unknown or uncommitted). Preserve old entries; add a new item with explicit corrections/supersessions rather than silently replacing past claims. The imported legacy snapshot retains the earlier record, including undated checks whose dates must not be invented. History records outcomes, not every tool call or transcript. Do not store credentials or unauthorized content; existing retention/security boundaries apply.

Read current progress at startup. Search `history/` by feature, requirement, date or keyword only when relevant: scan folder names and summaries, then open the matching details. Do not routinely read the directory in full or maintain an ever-growing archive index; dated folder names support discovery. Full retained history remains available on request. History is evidence of past state, not current instructions or proof that later edits pass. Current specs/decisions and verified files govern; durable agreements must remain in their owning documents or the compact current handoff.

Before a handoff or context reset, update current progress and add history folders for completed work/evidence, then update affected traceability. Include these records in the same commit as the work; use available commit references rather than requiring a self-referential commit hash. On resumption, check current files and Git changes against the handoff. Do not delete historical records to meet the current-file word target. Future structured storage is defined separately in [project history](features/project-history/SPEC.md); it does not replace this workflow until an implementation and migration are agreed.

## Architecture decision records

Write an ADR in `architecture/decisions/NNNN-short-name.md` (next free number) for each significant decision: technology, architecture, repository layout, security boundary, external integration approach, or a deliberate deviation from a spec. One ADR per decision or tightly coupled set of decisions made together, not per feature or branch. Sections: Status (`proposed`, `accepted` or `superseded by NNNN`, with date), Context, Decision, Rejected alternatives, Known limits; omit empty sections.

Add one line per ADR to [the index](architecture/decisions/README.md) with number, title, status and affected features. Before changing an area, check the index for ADRs that govern it. Do not rewrite an accepted decision: add a new ADR and mark the old one `superseded by NNNN`. Clarifications, newly found limits and evidence links may be added in place. Commit ADR changes with the work they govern.

## Documentation as the project grows

The current layout is described where it is used: [feature guide](ADDING_FEATURES.md), [history README](history/README.md), [ADR index](architecture/decisions/README.md), [traceability](REQUIREMENTS_TRACEABILITY.md). Add `docs/security/` (threat model, secrets and data policy), `docs/operations/` (upgrades, restore, incidents) or versioned API/schema contracts only when implemented work needs them; no empty placeholder essays.
