# Developing the workspace inside itself

[Shared principles](../../PRINCIPLES.md) apply.

[Dependencies and related features](SUMMARY.md). Read affected contract sections when implementing.

The user plans to move development of this repository into the workspace as soon as it is ready. Today that happens in external agent apps that create a Git worktree per session. This feature keeps that safety when the workspace edits its own code while running.

## Requirements

- **selfdev-001 — Worktree per change (built 2026-10-19, [ADR 0014](../../architecture/decisions/0014-worktree-per-session.md)):** A session or task that changes the workspace's own repository MUST work in its own Git worktree and branch from the current `main`, never in the checkout the running app is started from. The workspace creates the worktree and starts the session in it, so isolation never depends on the agent remembering it. Sync with `main`, merging and cleanup of merged worktrees are the agent's work through its own Git tools; as a safety net (user, 2026-10-19) the workspace removes merged branches (squash-merged ones included, [#24](https://github.com/MomSesImSpcl/ai-workspace/issues/24); what counts as merged is governed by selfdev-010, which the built Git-history check does not meet yet, [#76](https://github.com/MomSesImSpcl/ai-workspace/issues/76)) without uncommitted changes and without a running agent at start (user, 2026-10-20: no daily run; merges arrive through Update and restart, which ends in a start), archives the chats of any removed branch (read only, under "Show archived"; unarchiving one makes its branch again under the same name from `main` at its next message, and a restored chat of the same branch joins it, while chats not restored stay archived under that branch, user 2026-10-21), never removes unmerged work on its own, and lists every branch of the app project with its state, size, folder and a Remove… that asks before losing work in Settings → General ([vcs-011](../version-control/SPEC.md)); the [version-control](../version-control/SPEC.md) UI MAY show them but is not needed (user, 2026-10-19). A worktree another active session uses is never removed, and the workspace notices when a session's worktree is gone. Built: the app adds the repository it runs from as a project at every start (first in the list, no menu), and only that project's sessions get a worktree in workspace storage on branch `aiws/<session id>` from the checkout's HEAD, made at its first turn with a notice in the chat; a chat's tasks and their subtasks share it; a worktree gone after that stops the session with an error. A new chat starts only after the user names a new worktree (the name is also its branch: letters, digits, `.`, `_`, `-`; empty, invalid or taken names are refused with a message) or picks an existing workspace-made one to continue, both left in the Send row; the sessions list groups the project's chats under one heading per worktree (2026-10-19). A new worktree gets its npm dependencies (`npm ci` where a `package-lock.json` is, run by the app outside the agent's sandbox) before the agent starts, with notices in the chat; a failed install is reported and does not stop the session ([#26](https://github.com/MomSesImSpcl/ai-workspace/issues/26), 2026-10-20).
- **selfdev-002 — Running instance untouched (built 2026-10-19, [ADR 0015](../../architecture/decisions/0015-write-guard.md)):** Agent edits, installs and builds MUST NOT change the files, dependencies or storage of the running instance. Tool-broker path checks enforce this for the agent's tools; it is not left to model instructions ([architecture 3.3](../../ARCHITECTURE.md#33-data-isolation-and-data-classification)). Built: every session and task is guarded against writes to the app's checkout and the workspace's storage outside its own folder; Claude Code through a `PreToolUse` hook that also holds in bypass mode, Codex by declining such approval requests and running worktree sessions in its `workspace-write` sandbox without approvals instead of full access, with the checkout's `.git` parts a commit needs writable (tested on Windows with both real agents 2026-10-20). Commands that only read pass; every blocked write is shown in the chat with the command or file. To keep such notices rare, worktree agents are told the guard's rules up front: keep the shell in the worktree, write files with edit tools, keep merge commands out of command text (2026-10-23; the guard stays the limit). Shell commands are checked by the paths they name, so a path computed at run time is not seen ([#18](https://github.com/MomSesImSpcl/ai-workspace/issues/18)); such a write into the app's checkout is reported after the turn instead: the checkout's `git status` is compared before and after every app-project turn, and new changes show as a chat notice (2026-10-20; prevention not planned, the user accepted detection).
- **selfdev-003 — Verify in the worktree (built 2026-10-20 as a workspace rule, [ADR 0017](../../architecture/decisions/0017-merge-through-workspace.md)):** Before review, the agent runs the repository's own checks in the worktree (`npm run typecheck` and `npm test` in `app/` today) and reports the results in the chat, where they stay with the session or task as evidence. For UI changes, [ui-verification](../ui-verification/SPEC.md) against an instance started from the worktree MAY add screenshots.
- **selfdev-004 — Review before applying:** Merging into `main` needs the user's approval in the chat, under the existing approval and permission rules ([ADR 0004](../../architecture/decisions/0004-agent-native-permissions.md)); no agent merges its own change into the running app unasked. The agent commits and pushes its branch; changes reach `main` only through a pull request ([ADR 0016](../../architecture/decisions/0016-main-ruleset.md)). Built 2026-10-20 ([ADR 0017](../../architecture/decisions/0017-merge-through-workspace.md)): the agent calls the workspace tool `request_merge` with its check results; it opens the pull request if needed, shows one approval card, and on Allow the app squash-merges it. Agents cannot run `gh pr merge` themselves (guard; no `gh` login in Codex's worktree shells; limits in [#31](https://github.com/MomSesImSpcl/ai-workspace/issues/31)). The merge note tells agents never to merge in any other way (GitHub API, curl, a push to `main`); a determined agent could still work around it, an accepted limit (user, 2026-10-20). Every session and task, the orchestrator included, gets the read-only workspace tool `read_repo` (commit history, commits, branches with worktrees and ahead/behind counts, and `git status --short` of the checkout or a project worktree through git; pull requests with checks and failed log lines, and issues, through gh) for any workspace project, since the orchestrator runs no commands and Codex's worktree shells have no gh login.
- **selfdev-005 — Apply by restart (built 2026-10-20, [ADR 0018](../../architecture/decisions/0018-restart-and-fallback.md)):** After merge, the running app offers a restart onto the new code. Sessions and tasks MUST survive it: running turns are either finished first or recorded as interrupted and resumable ([sessions](../sessions/SPEC.md), [task-runtime](../task-runtime/SPEC.md)). The session that requested the restart continues afterwards. Built: in the desktop app run from a checkout, the toolbar's "Check for updates" fetches `main` only when clicked (no background checks; user, 2026-10-20). It turns into "Update and restart" when `main` has commits the checkout lacks, or waits ("Waiting for merge", asked again every 10 s, at most 10 minutes) while a pull request with auto-merge runs its checks. Not on `main` or with changes in `app/`, it does nothing and its tooltip says why. "Update and restart" is a fast-forward of the checkout (refused on another branch, with uncommitted changes in `app/` or local commits), changed dependencies installed, then a restart. Session and task hosts are detached and keep running through it; they keep their old code until they end ([#37](https://github.com/MomSesImSpcl/ai-workspace/issues/37)).
- **selfdev-006 — Fall back (built 2026-10-20, [ADR 0018](../../architecture/decisions/0018-restart-and-fallback.md)):** If the new version fails to start or fails its startup check, the user MUST be able to start the last working version (the last `main` commit that passed its startup check; user, 2026-10-20) without manual Git work, and see why the new one failed. Storage format changes need a migration that the previous version tolerates or a backup taken before the restart ([workspace-transfer](../workspace-transfer/SPEC.md)); agreed 2026-10-20: a backup only before a version with a storage migration, not built ([#37](https://github.com/MomSesImSpcl/ai-workspace/issues/37)). Built: the startup check is basic (user, 2026-10-20): the UI server starts and the page reads projects, tasks and sessions within 60 s. A restart keeps the old instance until the new one passes; on a failure the old one, or a failed cold start itself, shows why and offers the last working version, a copy kept in workspace storage with its own dependencies and Electron.
- **selfdev-007 — Not only this repository (deferred 2026-10-19 by the user: only the app project works in worktrees, ADR 0014):** The same flow applies to any project whose running app the user develops in the workspace; this workspace is the first case.
- **selfdev-008 — Binding stays true (built 2026-10-22, [ADR 0019](../../architecture/decisions/0019-binding-check-and-continuation.md), [#62](https://github.com/MomSesImSpcl/ai-workspace/issues/62)):** Before the workspace runs work in a session's worktree or publishes its branch, it MUST check the session's stored binding against Git: the project is still the app project, the folder is a worktree the workspace keeps for it in the project's repository, it still exists, it has the stored branch checked out, and that branch's work is not already merged. A mismatch MUST stop the work or publication with the session, project, folder, stored and actual branch, the work the folder keeps and the way on; Git HEAD MUST NOT be trusted in place of the stored branch, and nothing is switched, reset, deleted or moved. A chat with a stale binding MAY continue only in a new chat the user picks and confirms: on a new branch from freshly fetched `origin/main`, or on an existing workspace branch that passes the same check; the new chat gets the conversation, the old chat keeps its binding, and uncommitted work is not transferred. Continuation grants no permissions and bypasses no approval, check, up-to-date or merged-PR guard; publication is checked again after the approval card. Built: the check runs at every turn of chats and tasks and before and after the `request_merge` card; "Continue in a new chat" appears under a chat whose turn was stopped this way or whose branch was removed, and is refused while the chat works. The turn-start merged check covers pushed branches with a reachable gh ([#69](https://github.com/MomSesImSpcl/ai-workspace/issues/69)). Automated tests only; not yet verified in the app with real agents and a real pull request.
- **selfdev-009 — Test instance of a branch (specified and built 2026-10-23 at the user's request):** The user can run a branch's code as a second app window next to the main one, to try a change before it merges. The heading of a branch in the app project's session list has a menu (right-click, or its ⋯ button on hover) with **Open test instance**, shown only while that branch's worktree folder exists, at least one of its chats is not archived, and its dependencies are installed (every folder with a `package-lock.json` has a finished `npm ci`, also after a restored branch was made again), and never inside a test instance. The instance runs the worktree's own app code with its own storage folder (`<storage>/test/<branch>`) and Electron data folder, so it never reads or changes the main instance's projects, chats or tasks; it starts empty except for the workspace settings (roles, agent setup, instructions, workspace folder), copied from the main instance at every start, and changes made there never flow back. It uses the agents and logins of the user's computer, as the main instance does. Its title reads `Test Branch - <branch>`, Check for updates and Update and restart are not shown in it, and it records no last working version. One test instance per branch: opening it again brings the open window to the front. Its storage folder is removed with the branch. The worktree's code decides what the instance does: a branch made before this requirement shows neither the title nor the hidden buttons.
- **selfdev-010 — Cleanup only with merge evidence (specified 2026-10-23 by the user, not built; M1 blocker [#76](https://github.com/MomSesImSpcl/ai-workspace/issues/76), [ADR 0021](../../architecture/decisions/0021-cleanup-needs-merge-evidence.md)):** The automatic removal of selfdev-001's safety net MUST remove a branch and its worktree only on positive evidence that the branch was intentionally merged: a pull request of that branch into `main` that GitHub reports as merged, confirmed against the app project's current repository and base, and tied to the current branch/worktree binding (the binding the workspace made for that worktree and branch, with its creation commit and time), not to the branch name alone. A merge through `request_merge` is recorded with that binding (repository, base, branch, worktree, pull request number, its head commit and merge commit) once GitHub confirms it; a merge done outside the workspace counts once the workspace verifies it the same way. Evidence never carries over from an earlier binding: a reused branch name or worktree folder gets no eligibility from a pull request that merged before the current binding was made, or whose head is not a commit of the current binding made after its creation commit. Ancestry in `main`, matching trees, a `git merge-tree` no-op, or a branch updated from `main` (fast-forward or merge commit) are never evidence on their own. Even with evidence, the branch is removed only when its tip is the evidenced pull request's head (no work after the merge), its folder has no uncommitted changes and no agent works in it. Missing, uncertain or unavailable evidence (gh not installed, not logged in or offline, an API error, no matching pull request) keeps the branch; branches that exist before this is built stay unless they get such evidence. Removal by the user through Settings → General → Remove… is separate and keeps its own confirmation. Acceptance (each by automated test, then once in the app): (1) a fresh branch without commits of its own, updated from `main`, clean and idle, is kept; (2) a clean, idle branch with a verified merged pull request, squash merge included, is removed at start; (3) a branch with commits after the evidenced merge is kept; (4) a branch with uncommitted changes or a working agent is kept; (5) with the evidence unavailable the branch is kept; (6) a branch name or worktree reused after an earlier merged pull request of that name is kept until its own pull request merges.

Agent dependence: worktree work, approvals and interruption rely on the [integration matrix](../../INTEGRATIONS.md) rows "Own tools, settings and permissions (ADR 0004)", "Relay "ask" prompts as approval cards" and "Stop a turn"; agents without approval relay fall back to the workspace approval check before merge.

## Acceptance evidence

- From a workspace session, an agent changes a UI label in a new worktree; typecheck, tests and a UI check pass there; the running app is unchanged until the user approves the merge.
- After approval and restart, the app runs the new code and the session that made the change continues with its history.
- A change that breaks startup leads to an offer to start the previous version, with the error shown.

## Non-goals and open decisions

- No automatic merge or deploy without approval; no hot code swap of the running process.
- Decided 2026-10-19 ([ADR 0014](../../architecture/decisions/0014-worktree-per-session.md)): worktrees live in workspace storage, only the app project uses them, a chat's tasks share its worktree.
- Open: contents of the startup check; whether the previous version runs from a kept worktree or a fresh checkout of the previous commit.
- Using the workspace on its own repository after the core was proposed earlier and is still not an agreed delivery order ([proposal record](../../history/2026-10-16-00-imported-progress-snapshot/DETAILS.md#proposed-not-yet-agreed)).
