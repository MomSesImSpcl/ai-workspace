# Agent setup onboarding and readiness in the UI

[Shared principles](../../PRINCIPLES.md) and [related features](SUMMARY.md) apply.

## Problem

The user assigns any agent integration to any role ([routing-001](../model-routing/SPEC.md#role-and-agent-assignments)), so no agent CLI is a direct dependency ([dependency inventory](../../DEPENDENCIES.md#agent-integrations-optional-users-choice)). Today nothing in the UI says this. A new user sees role names (`Orchestration`, `Implementation`) without knowing what they do, cannot tell which agents are installed or logged in, and only learns about a missing or logged-out agent when a started task fails.

## Proposed solution (agreed direction, not yet designed in detail)

Explain agents at the three places where the user makes a choice, all fed by one readiness check. No separate help page is needed to understand the basics.

## Requirements

- **onboarding-001 — One readiness source:** The UI MUST get agent status from the prerequisite check ([distribution-001](../distribution/SPEC.md#requirements-for-a-selected-implementation)), exposed through the local API, and MUST NOT guess. Per integration it reports one of: `ready` (with tested/installed version), `not-installed`, `not-logged-in`, `untested-version` (usable, with a warning), or `no-adapter` (such as `manual-browser`). The check runs on app start and on demand ("Check again"); it never installs software or logs in.
- **onboarding-002 — First-start agent setup:** When no runnable integration is `ready`, the app MUST open an "Agents" setup step instead of an empty workspace. It shows one card per supported integration with its status and the exact next action: a copy-ready install command for `not-installed`, and a button that starts the vendor's own login flow for `not-logged-in`. The heading states the rule in one plain sentence, for example "You need at least one agent. Each one uses your own subscription." Continuing MUST be possible once one integration is `ready`. The user can reopen this step later from Settings.
- **onboarding-003 — Roles as plain jobs:** Settings MUST present each role as the job it does, with the technical role name secondary, for example "Plans and splits work (Orchestration)" and "Writes and changes code (Implementation)". Each role's agent picker shows every integration with its readiness; integrations that are not `ready` stay selectable but are marked with the reason and a link to fix it. A role assigned to a non-ready integration MUST show a visible warning in Settings.
- **onboarding-004 — Readiness before starting a task:** The new-task composer MUST show which agent will run the task ("Runs with Claude Code · Implementation"). If that integration is not `ready`, the composer MUST replace the start action with a fix action (for example "Set up Claude Code first") and MUST NOT create a task that is known to fail for this reason.
- **onboarding-005 — Privacy:** Logins stay in the vendor's flow; the workspace never asks for, stores or displays subscription credentials or tokens. Status details MUST NOT expose account identifiers beyond what the vendor CLI shows the user anyway.
- **onboarding-006 — Agent detection and selection:** The readiness check MUST also detect which known agents are present on the computer: the agent CLIs the workspace has adapters for, looked up on `PATH` and in each vendor's documented default install locations per OS. Detected agents MUST appear first in every agent selection (first-start step, role pickers), labeled "Found on this computer" with their version; agents not found stay listed below with how to get them. Detection only reads: it MUST NOT run anything beyond a version or login-status command, MUST NOT scan the user's files or other folders, and MUST NOT send results anywhere. Agent products the workspace has no adapter for MAY be shown as "Found, not supported yet" so the user knows why they cannot be picked.
- **onboarding-007 — Agent-specific readiness:** Beyond installed and logged in, the check MUST report known per-agent setup gaps that break features, with the exact fix. First case: Codex on Windows whose `codex doctor` reports "sandbox backend disabled" is marked `needs-setup` ("Codex can't write files on this PC") with the config change from the [dependency inventory](../../DEPENDENCIES.md#agent-integrations-optional-users-choice). The check only runs read-only diagnostics; it never changes the agent's config.
- **onboarding-008 — Model and effort catalog:** Setting up an agent for the workspace MUST record what it offers: its models (id and label, including the user's configured default) and, per model, the effort levels it accepts, read from the agent itself where it can list them (for example `codex debug models`) and otherwise from its documented options. The catalog is refreshed when the agent or its configuration changes. Pickers in sessions and tasks and the orchestrator's suggestions ([orchestrator-004](../ai-orchestrator/SPEC.md)) use only this catalog; it is a required row of the [integration matrix](../../INTEGRATIONS.md).
- **onboarding-009 — Token cost weights:** Setting up an agent MUST also record, with its catalog (onboarding-008), how its provider prices token kinds relative to a normal input token: prompt-cache read, prompt-cache write and output, per model where they differ, with the source and the date read. Token budgets and every token display use these weights ([task-runtime 4.6](../task-runtime/SPEC.md#46-scheduling-and-budgets)); without recorded weights the workspace uses its documented default (cache read 0.1, cache write 1.25, output 1) and labels the figures as estimates. The weights are refreshed with the catalog and never presented as a verified price. The hover breakdown of a token figure (added 2026-10-18) MUST follow the same agent and model: list only the token kinds that agent reports (for example no cache-write line for an agent without cache writes, a reasoning line where an agent reports reasoning tokens separately), each with its recorded weight, and say when the weights are the default estimate. Today every agent uses the defaults, and the breakdown always shows the four Anthropic kinds.
- **onboarding-010 — Agent setup inventory (built 2026-10-18):** The workspace MUST list what each agent loads besides its own prompt and tools, without a model call, each item with a short description: plugins, MCP servers (Claude Code: including claude.ai connectors; Codex: apps as one item), skills that do not come from a plugin as one item (Claude Code cannot switch single skills for one run; its only switch, `--disable-slash-commands`, also drops plugin and built-in skills, so it is used only when the role's global rules load the user's skills and no plugin of the run has skills; a standalone skill whose `SKILL.md` is identical to an installed plugin's skill is marked as its copy, fixed 2026-10-19), the user's hooks, the agent's built-in tools or optional built-in features, and its own system prompt. It MUST be able to switch each item off for one run. Claude Code: `claude plugin list --json`, `claude mcp list`, the user's `skills` folder and settings hooks. Codex app-server: `plugin/list`, `config/read`, `skills/list`. The list is refreshed at every orchestrator or task start and with **List again** in Settings, where each item's state is set ([orchestrator-005](../ai-orchestrator/SPEC.md#independently-selectable-roles)). Items not listed stay on. Per-item token costs are not measured (user, 2026-10-18): the measured totals per call show the saving.
- **onboarding-011 — What each agent loads anyway (specified 2026-10-19, not built):** The agent setup step MUST say per agent which of the user's own files the workspace cannot keep out of its runs ([orchestrator-005](../ai-orchestrator/SPEC.md#independently-selectable-roles), [#17](https://github.com/MomSesImSpcl/ai-workspace/issues/17)), in one short line each: Claude Code reads the user's global `CLAUDE.md` for a project inside the user's home folder (as a `.claude/CLAUDE.md` above the project), and Codex always reads its global `AGENTS.md`. When the user adds a project or sets the workspace folder inside the home folder while Claude Code is assigned to a role, the workspace MUST show a warning that Claude Code will read the global `CLAUDE.md` for projects there. It is only a warning and blocks nothing. The lines come from the integration matrix and change when an agent gains a switch.
- **onboarding-012 — Codex without the global AGENTS.md (specified 2026-10-19, not built; user: the 550 tokens per call add up and may grow):** Optional, off by default (user, 2026-10-19): by default Codex reads its global `AGENTS.md` as it does today. A Settings option, offered in the Codex setup step with what it does and needs, lets the user turn this on. Then, when a role's global-rules switch is off ([orchestrator-005](../ai-orchestrator/SPEC.md#independently-selectable-roles)), Codex runs start with the workspace's own Codex folder (`CODEX_HOME`), rebuilt at every start: the user's `config.toml` copied in, the user's plugins, skills and memories linked, on every supported OS (Windows: directory junctions, which need no admin rights or Developer Mode; macOS and Linux: symbolic links), and no global `AGENTS.md`. Task threads then live only in that folder. Login MUST stay in the user's control: the workspace uses this only when Codex keeps its login in the operating system's credential store (`cli_auth_credentials_store = "keyring"`, which the user sets; Windows Credential Manager, macOS Keychain, Linux Secret Service), so every Codex folder shares one login, and it never copies, moves or reads `auth.json` or other credentials (onboarding-005). With file-based login, Codex keeps the global AGENTS.md and Settings says why. First check with the real Codex on Windows, macOS and Linux: the keyring setting and shared login, the links, that Codex's own writes (memories, plugin cache, MCP OAuth tokens) still reach the user's files, and the saved tokens per call.
- **onboarding-013 — One item per hook (specified 2026-10-19, not built; user: tools such as rtk work through hooks and are hidden inside one "Your hooks" item):** Optional, offered in each agent's setup step with what it does and needs, off by default; the user wants it on for their own setup. When on, the inventory ([onboarding-010](#requirements)) lists each of the user's hooks as its own item instead of one "Your hooks" item, titled by its command (for example `rtk hook claude`) with its event and matcher, and each can be set per role and agent like other items ([orchestrator-005](../ai-orchestrator/SPEC.md#independently-selectable-roles)). Whether a single hook can be switched for one run depends on the agent, so the setup step MUST say per agent what applies:
  - **Claude Code:** the run's hooks are passed with `--settings`, so each hook is switched on its own. With the role's global rules on, the user's hooks cannot be switched for one run and stay on (as today).
  - **Codex (checked 2026-10-19 with Codex 0.163.0):** per-run config cannot remove a single hook. A `-c hooks.state.'<key>'.enabled=false` override is ignored ("session-flags: … is ignored"), and higher config layers only add hooks, never replace them. Single hooks can therefore be switched only in the workspace's own Codex folder of [onboarding-012](#requirements): its rebuild writes a `hooks.json` with only the run's hooks, and copies the trust entries (`hooks.state`, keyed by file, event, group and index with a `trusted_hash`) under their new keys, so only hooks the user already trusted run. The workspace MUST NOT use `--dangerously-bypass-hook-trust` or trust a hook the user has not trusted. Without that folder (onboarding-012 off, file-based login, or global rules on), Codex hooks stay one item, and the setup step says why.
  - First check with the real Codex: that a copied `trusted_hash` is accepted under the new key, and that a hook left out of the run's `hooks.json` does not run.

## Non-goals

Installing agent CLIs automatically, managing subscriptions or billing, recommending a specific vendor, and explaining model capabilities. Installers and packaging stay in [distribution](../distribution/SPEC.md).

## Open decisions

- Exact wording of role descriptions and the setup heading.
- How "start the vendor's login flow" works per CLI (open a terminal with the login command, or show the command to copy).
- Whether onboarding also asks for the first project, or leaves that to the existing empty state.

## Suggested increments

onboarding-001 with the onboarding-003 hints is the smallest useful slice; onboarding-002 and onboarding-004 build on the same check.

## Acceptance checks

- With no agent CLI on `PATH`, the app opens the Agents step; each card shows `not-installed` with an install command; Continue is disabled.
- After installing and logging in one CLI and pressing "Check again", that card shows `ready` and Continue works.
- Logging out of the agent assigned to `Implementation` shows a warning on that role in Settings, and the composer offers "Set up … first" instead of starting; no task file is created.
- An installed version different from the last tested one shows `untested-version` and still allows starting tasks.
- On Windows with Codex's sandbox not set up, Codex shows `needs-setup` with the config change; after the user applies it and presses "Check again", it shows `ready`.
- With Claude Code installed in its default location but not on `PATH`, and Codex not installed, the role picker lists Claude Code under "Found on this computer" (with version) above Codex; detection created no files and made no network calls.
